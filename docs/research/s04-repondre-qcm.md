# Research — Story s04-repondre-qcm

## The five structuring facts

1. **Le QCM est persistant avec `questions` JSON dans `Exercise.questions` (s03)** — `Exercise.questions` est `Mapped[list[dict[str, Any]] | None]` (`backend/app/core/database/models.py:133`). Chaque dict a les clés `question`/`options`/`correct_index` (cf. `QcmQuestion` dans `qcm_generator.py:45-50`). Pour grader, le grader lit `Exercise.questions` depuis la session, reconstruit la liste de `correct_index` (un `int` par question), compare avec les `raw_answers` de l'élève.
2. **L'AC2 dit "is_success is `true` if and only if ALL answers match"** — c'est un ET logique sur tous les `correct_index`. Pas de score partiel. Pour 5 questions, l'élève doit avoir 5/5 pour valider. C'est le QCM "tout-ou-rien" mentionné dans la story.
3. **L'AC3 dit "attempt_number is incremented correctly across multiple submissions on the same exercise"** — la numérotation est par `(pseudo, exercise_id)`, pas globale. Le `QcmGrader.grade` doit faire un `SELECT COUNT(*)` ou `SELECT MAX(attempt_number)` sur les `Attempt` existants pour ce couple avant d'insérer. **C'est le piège #1** de la story : un simple `len(self._all_attempts)` global incrémenterait mal.
4. **L'AC6 dit "pseudo_a cannot submit a QCM generated by pseudo_b"** — multi-tenancy. Le grader doit vérifier que `Exercise.student_pseudo == pseudo` avant de grader. Sinon, un élève A peut deviner un UUID d'exercise et soumettre ses réponses (mécanisme de "test attack" classique).
5. **Le scoring est 100% déterministe** — pas d'appel LLM. `qcm_generator.py` est volontairement narrow ; s04 doit l'être aussi. La story le dit explicitement ("QCM scoring is DETERMINISTIC — no LLM call. Resist the temptation to 'improve' with an LLM").

## Target story

**Story** : s04-repondre-qcm — Soumettre une réponse à un QCM et obtenir un verdict binaire.
**Complexity** : 2 (Persistence + comparison + JSON in/out. No LLM call for QCM scoring).

### Acceptance criteria (6 ACs)

1. CLI : `python -m ktutor.cli submit-qcm --exercise-id <id> --answers '[0,2,1,3,0]'` retourne `{is_success: true|false, correct_count: int, total: int, feedback: string}`.
2. `is_success` est `true` si et seulement si TOUTES les réponses matchent `correct_index` pour TOUTES les questions.
3. L'attempt est persisté en PostgreSQL avec : `pseudo`, `exercise_id`, `attempt_number`, `is_success`, `submitted_at`, `raw_answers`.
4. Un test vérifie qu'un score parfait retourne `is_success: true` et un score avec une seule mauvaise réponse retourne `is_success: false`.
5. Un test vérifie que `attempt_number` est incrémenté correctement à travers plusieurs soumissions sur le même exercise.
6. Un test vérifie que `pseudo_a` ne peut pas soumettre un QCM généré par `pseudo_b` (isolation multi-tenant).

## Traps & constraints

- **AC5 : `attempt_number` est par `(pseudo, exercise_id)`**, pas global. Le piège : si le grader fait `len(session.new)` ou un compteur en mémoire, il sera faux après le commit. Solution : `SELECT MAX(attempt_number) FROM attempts WHERE exercise_id = ? AND student_pseudo = ?` + 1. Ou `SELECT COUNT(*)` + 1 (équivalent). Le test AC5 vérifie qu'après 2 soumissions, `attempt_number == 2`.
- **AC6 : cross-tenant**. Le grader doit lever `QcmGradingError("cross_tenant", ...)` si `Exercise.student_pseudo != pseudo`. **Note** : la story dit "raises 409" en passant (s08 progressive correction), mais pour s04 c'est `QcmGradingError("cross_tenant")` qui mappe sur exit 5 (cohérent avec s03 `document_not_found` → exit 5).
- **Validation des `raw_answers`** : c'est une `list[int]` de longueur = `len(Exercise.questions)`. Valeurs dans `[0, 3]`. Le piège : si l'élève envoie `[0, 1, 2, 3]` (4 réponses) mais le QCM a 5 questions, le grader doit lever `QcmGradingError("invalid_answers")`. Idem si la longueur est 0 ou > len(questions). Idem si une valeur est hors `[0, 3]`. **Pydantic `field_validator` est le bon outil**.
- **Le grading doit-il re-valider `Exercise.questions` via `QcmQuestion` Pydantic ?** Oui : si pour une raison quelconque la DB contient un QCM malformé (ex. migration mal passée), le grader doit lever une erreur claire plutôt que crasher. Mais c'est un defense-in-depth — le test AC4 et AC5 utilisent des QCM bien formés. À confirmer au planning.
- **Pas d'appel LLM** : le `QcmGrader` n'a pas besoin de LLM. Pas d'injection `llm=...` dans le constructeur. Plus simple que `QcmGenerator`.
- **CLI flag `--answers`** : format `'[0,2,1,3,0]'` (string JSON, comme `--question` pour s02). Typer parse via `typer.Option(..., callback=...)` ou en string puis `json.loads`. Proposition : `typer.Option(...)` de type `str` puis `json.loads` dans le handler (cohérent avec `--json` ailleurs).
- **Exit codes** : la documentation du CLI (ligne 5-15 de cli.py) liste déjà les codes existants (0-5). s04 doit mapper `QcmGradingError.kind` sur ces codes :
  - `invalid_answers` → 4 (storage_failure) ou 2 (invalid_file) ? Le code 2 est "invalid file" (extension, taille). Le code 4 est "ChromaDB or PostgreSQL write failure (or LLM malformed output)". **Le plus proche est 4** (mauvais input sémantique, pas invalid file). Mais s03 a utilisé 5 pour `document_not_found`. Pour rester cohérent, on peut introduire 6 = "invalid input" ou utiliser 5 (invalid pseudo) — le grader considère que des `raw_answers` malformés sont une erreur de l'utilisateur au même titre qu'un pseudo invalide. **À trancher au planning**.
- **Cohérence nommage** : `qcm_grader.py` (verbe d'action) plutôt que `qcm_grading.py` (nom abstrait). Cohérent avec `qcm_generator.py`. Le nom `QcmGrader` (verbe) suit le pattern. Alternative : `QcmSubmitter` (verbe d'action métier), mais `Grader` est plus précis sur le rôle.
- **Stockage `raw_answers`** : `list[int]` (5 entiers pour 5 questions). `sqlalchemy.JSON` (portable, cf. Exercise.questions). Type Pydantic `attempt_number: int` avec `Field(ge=1)`.

## Open questions

1. **Exit code pour `invalid_answers`** : 4 (storage_failure) ou 5 (invalid pseudo) ou nouveau code 6 ? Proposition : 4, car "mauvais input sur l'exercice" est plus proche d'une erreur de write que d'une erreur de pseudo. **À trancher au planning.**
2. **Re-validation Pydantic des `Exercise.questions`** : oui ou non ? Proposition : oui, en defense-in-depth. Coût : 1 test, pas de risque de régression.
3. **Modèle `Attempt.answer_text`** : l'architecture cible l'inclut (TEXT nullable). Pour s04 (QCM), pas nécessaire. Le grader le laisse à `None`. La story ne l'exige pas. Proposition : ajouter la colonne `answer_text: Mapped[str | None] = mapped_column(String(8192), nullable=True)` (cohérent avec l'archi cible, prête pour s07).
4. **Modèle `Attempt.correction_level`** : idem, l'archi le veut ("partial" | "full" | ...). Pour s04, jamais utilisé (la correction progressive arrive en s08). Proposition : ajouter la colonne `correction_level: Mapped[str | None] = mapped_column(String(32), nullable=True)` (cohérent avec l'archi, prête pour s08). Ou différer à s08 et faire une migration de colonne à ce moment-là.
5. **CLI : où afficher la sortie ?** : stdout via rich.Panel avec un récap (score X/Y, is_success ✓/✗, feedback textuel), ou JSON via `--json`. Le plan s03 a utilisé `panel rich` pour la sortie "humain" et `console.print_json` pour `--json`. Même pattern pour s04.
6. **Feedback textuel** : "Toutes les réponses sont correctes" pour `is_success=True`, "X/Y réponses correctes" pour `is_success=False` ? Proposition : feedback informatif qui résume le score, pas un message moralisateur.
7. **Le QCM "tout-ou-rien"** : la story insiste sur "is_success est true ssi TOUTES les réponses matchent". Pas de score partiel. Mais l'AC1 demande `correct_count: int, total: int` — donc on **affiche** le compteur X/Y, mais `is_success` n'est `true` que si X==Y. Proposition : c'est la lecture littérale de l'AC.
8. **Cohérence attempt_number** : sur le premier submission, `attempt_number == 1`. Sur le deuxième, `attempt_number == 2`. Pas de "retry" automatique. Le grading s04 ne modifie pas `is_success` après coup. Proposition : comportement standard.
9. **Validation des `raw_answers` à la frontière CLI** : le CLI parse `'[0,2,1,3,0]'` (string JSON) en `list[int]`. Si invalide, lever une erreur avant d'appeler le grader. Pydantic `conint(ge=0, le=3)` pour chaque élément. Proposition : utiliser un Pydantic `SubmittedAnswers` (list[int]) construit dans le CLI.
10. **Migration Alembic** : la table `attempts` est nouvelle, comme `exercises` en s03. Pas de migration Alembic (cohérent avec s03). `init_db()` crée la table en dev/CI. Le follow-up Alembic arrivera en s15.

### Vérification manuelle (humain)

- Générer un QCM (depuis s03).
- Soumettre les bonnes réponses → `is_success: true`, `correct_count: 5`, `total: 5`.

- Soumettre 2 fois de suite → vérifier `attempt_number: 1` puis `attempt_number: 2`.
- Soumettre avec un mauvais pseudo → erreur cross-tenant.
